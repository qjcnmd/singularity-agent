# 研发流程复盘与硬化

所有规则、检查或流程改动均须经用户确认后再实施。

## 1. 收集运行证据

* 读取 `.reviews/` 下的结构化审查档案（YAML 元数据 + 完整 `# Review Brief` 与 `# Review Report`，覆盖 `codex` 与 `subagent` 两种通道），归纳反复出现的问题类目、驳回/过度防御模式、简报缺口及耗时/异常趋势。
* 扫描近期 Git 历史中的修复、回滚与审查返工提交：
  ```powershell
  git log -n 30 --stat --oneline
  ```
* 结合用户指出的痛点或具体卡顿会话（如有）。若近期无明显共性问题或流程瓶颈，直接汇报健康并结束。

## 2. 按四级由硬到软选最高解法（每次 1～3 条）

兼顾**模型高频反复犯错**与**外层工作流自身的低效/跑偏/冗余**，筛选有真实证据支撑的高杠杆改进项（每次克制在 **1～3 条**），按从硬到软顺序选**最高能根治的层级**（每条必须说明为何更高一层不适用）：

1. **架构消除**：统一单一来源、收紧模块可见性、删除易被抄错的旧路径或死代码，使错误从结构上写不出来；
2. **类型 / Lint / 检查脚本拦截**：用 Rust/TS 类型约束、Clippy、oxlint 或 `scripts/check.ps1` 拦截，且报错信息直接指出正确做法；
3. **行为不变量测试**：补充外部黑盒或 `proptest` 不变量测试（遵守 `docs/development.md` 测试保留标准）；
4. **工作流、模板与规则校准（最后）**：迭代固定流程与模板（`wf-dev/SKILL.md`、`wf-dev/review-rubric.md`、`wf-qa/SKILL.md`）；校准审查尺度或高频误报（将低价值边界记入 `docs/decisions.md`）、简化脚本或步骤、微调 `AGENTS.md`；**凡已被前三级彻底封死或长期失效的旧文字规则/步骤，一并提议删除**。

## 3. 拍板与验证落地

* 用白话呈现每条建议（证据来源与频次、所选层级及为何不用更高一层、实施效果与维护代价），向用户确认采纳项。
* 用户确认实施后：
  * **新增的检查脚本或测试，必须先在对应历史错例上证明能真实报红拦截**，再确保当前仓库通过 `scripts/check.ps1` 与 CI 一致命令；
  * 改动工作流脚本（如 `scripts/codex-review.ps1`）时，用隔离用例实测正反路径与兼容性；收口按 `wf-dev` §2–§3 由用户选择审查方式（改工作流自身优先推荐空白上下文子代理）。
