# 已确认的取舍

这里记录已经讨论过、决定保留的设计和接受的行为限制。审查、修复或精简时，这些条目不当作缺陷，也不再提议修改。用户要求改变，或者表中写的前提不再成立时，说明具体差异后再讨论。

## 当前接受的行为限制

| 行为 | 适用条件与影响 | 源码入口 |
| --- | --- | --- |
| 压缩依靠模型遵守摘要指令，不单独拒绝工具调用 | 摘要请求保留工具定义。回复未截断且正文非空时，保存正文，不执行其中的工具调用。正文替换此前的模型上下文，完整历史仍在日志中。 | [compaction.rs](../crates/agent/src/compaction.rs) |
| 流解码失败时不保留已收到的 Token 用量 | 解码失败的请求保留错误和计时，但不记录解码器已收到的用量，累计统计可能低于实际消耗。未上报的用量保持未知。 | [provider.rs](../crates/model/src/openai/provider.rs)、[Chat 解码器](../crates/model/src/openai/chat/stream.rs)、[Responses 解码器](../crates/model/src/openai/responses/stream.rs) |
| 创建日志时被强制终止可能留下不完整文件 | 新会话独占新建日志并直接写入；创建过程中被强制终止时需要手动删除该日志，不增加创建事务或恢复流程。 | [manager.rs](../crates/agent/src/session/manager.rs) |
| 草稿存储错误不打断操作 | 首次读取失败时从空白继续，不提示、不禁用输入；新输入照常保存，允许覆盖当前任务的旧草稿。自动保存失败时保留当前输入，清理失败不影响已完成的任务删除或项目移除。 | [drafts.ts](../apps/desktop/src/drafts.ts) |
| 单份任务记录读取失败时，任务列表直接报错 | 末尾没有换行的不完整记录仍会忽略；完整记录解析或读取失败时，列表显示文件错误，不增加跳过任务和局部列表的处理流程。 | [thread_catalog.rs](../crates/app/src/runtime/thread_catalog.rs)、[file.rs](../crates/agent/src/session/file.rs) |
| 已显示部分输出后仍移除片段并自动重试 | 用户明确选择自动恢复：遇到已知暂时故障，移除本次未完成的正文和思考，重新生成整次回复；最多尝试三次，等待期间可停止，不单独提示重试。 | [request_execution.rs](../crates/agent/src/request_execution.rs) |

## 摘要请求保留指令和工具定义

摘要请求沿用本轮普通请求的指令和工具定义（做法见[架构说明](architecture.md#摘要请求与缓存)）。这样请求前缀和普通请求相同，尽量命中提供方的前缀缓存。代价是工具定义也计入摘要请求的输入和窗口预算；能否命中、能省多少取决于提供方。

只有用户要求改变，或用真实请求测出新的成本问题时才重新讨论。“摘要不执行工具调用”或“参考项目用了别的做法”都不构成移除工具定义的理由。

## 保留的设计

| 对象 | 依据 | 前提 |
| --- | --- | --- |
| Chat / Responses 流的字段形状检查 | 提供方响应是外部输入，字段类型不对时报错比静默丢内容更容易排查 | 仍直接对接第三方兼容端点 |
| 会话写入失败后拒绝后续写入（`append_error`） | 失败可能留下半行；继续追加会把半行夹在中间，下次打开整份日志解析失败 | 日志仍以换行作为一行完成的标记 |
| 完整目录读取时解析全部会话日志 | 不用维护索引；模型保存、任务改名和结束使用局部结果 | 任务变多、刷新列表明显变慢时，用真实数据实测后再决定 |
| 协议方法表里的 `directory.pick` | 方法表同时生成前端的 RPC 类型；该方法由 Electron 处理，后端收到时返回错误 | 前端类型仍从这张表生成 |
| `SessionData` 与 `SessionManager` 分开 | 列表和预览只读打开日志，不能截断未完成的末尾；写入能力只属于持有写者的一方 | 列表仍直接读取日志文件 |
| 前端读取与事件的序号比较和暂存回放 | 读取响应和实时事件可能交错到达，需要按全局序号丢弃过时数据 | 后端仍通过事件流推送增量 |
| 输入队列只保存在内存中，消息保存成功后才消费 | 接受后立即返回并显示“已接受”，再由回合保存；没来得及保存的输入靠前端草稿恢复 | “未保存的输入不恢复”仍是可接受行为 |
| 开始保存结果前锁定已接受的停止 | 同一时刻停止和保存只能有一个生效，避免出现保存了一半的中断结果 | 回合仍只有已保存的结果对外可见 |
| MCP 连接按工作目录复用、每轮重新发现工具目录 | 复用连接省掉每轮重连；每轮发现让工具目录反映当前配置，不依赖缓存 | 仍按工作目录区分连接 |
| 最多同时执行八个工具 | 用户明确选择并发执行，以减少多个独立工具调用的等待；不改为默认串行 | 普通工具并发，交互提问沿用现有等待规则 |
| 下拉框的选择、方向键和展开动画 | 浏览器负责关闭与层叠，业务仍需处理选择、滑块保存和现有动效 | 模型与协议的操作保持现有设计 |
| 用户显式引用技能时仍由模型读取正文 | 正文中的技能引用只展开为 `read` 加文件路径，不由程序注入技能全文 | 技能引用仍按当前目录解析，界面显示原文 |
| 用户输入与后台命令完成通知共用队列 | 通知在下一次请求前写入对话，避免插在当前一批工具结果之间；不用再处理两套输入的顺序 | 工具仍并发执行，后台通知仍进入模型上下文 |
| 请求准备与工具执行分开 | 手动压缩先检查旧对话，无需压缩时不加载目录，也不构造输入队列、提问和命令执行状态 | 手动压缩仍可独立运行 |
| 工具结果完成即保存，请求时按调用 ID 配对 | 慢工具不拖住已完成结果的保存和反馈；改成按调用顺序保存需要额外暂存结果 | 工具仍并发执行，完成结果立即保存 |
| 实时累计用量，读取历史时重新统计 | 累计供运行状态直接读取；重算覆盖消息已保存、用量事件尚未发布的读取窗口 | 保存与事件发布仍分开执行 |
