# 两种综合设计，而不是研究方案目录

## 1. 最终问题定义与选择依据

目标不是让摘要看起来更先进，而是同时降低**无用材料进入模型的体积、进入后被重复携带的次数、退役后恢复证据的难度**。原始历史永久保存与模型每次看到完整历史是不同职责。

保留当前 Summary 作为独立 baseline。新策略在 Session 创建前选定，之后不可变；不引入 embedding/vector DB；不以每步额外模型请求维护状态。当前用户已允许持续状态更新，因此旧的“只在压缩阈值更新”不再是约束。

前几轮方案的问题是把实现维度变成产品方案：笔记、状态、刷新频率、原文外置其实不是四个互斥答案。这里先固定共同结构，再只留下一个重要的设计分歧：**当前工作主要由语义状态承接，还是由原始证据承接。**

推荐顺序：状态工作集优先；原文工作集作为真正有竞争力的备选。这个排序是根据机制与成本作出的工程判断，不是实测任务排名。

## 2. 共同架构

```text
实际工具/用户/模型输出
        │ 先保存已捕获的原始数据
        ▼
SessionWriter：唯一追加日志 + 会话拥有的 payload
        ├── 真实执行结果 ──> 确定性事实归约
        ├── 原始来源 ─────> 可重建 metadata/FTS 索引 ──> history_search/read
        └── 已提交模型意图 ─> 工作状态/原文保留关系
                                      │
                               ContextController
                                      │
                        固定快照 + 有界增量 + 待处理观察
                                      │
                         合法 ModelTurnRequest / private replay
                                      │
                                正常模型决策
```

只有一个执行循环、一条真实工具路径和一个 SessionWriter。候选不是独立 Agent，也不是额外的每步审查模型。语义状态与索引都是日志的投影；不存在另一个可任意修改的事实数据库。

### 2.1 内容按职责分开

- 任务契约：当前目标、有效用户约束、验收要求。由原始用户输入支撑，模型不能自行宣布约束已经作废。
- 执行事实：命令的实际结果、已观察版本、验证证据、尚未完成的操作。来自工具而非模型的“我已经做完”。
- 工作判断：假设、决定理由、当前问题、下一步。显式标为模型判断，可被新证据修订。
- 原文材料：代码、错误、diff、用户措辞、局部对话。仍需直接推理的内容不强行归纳。
- 完整轨迹：全部原始记录、状态变更、选择记录。留在存储层，需要时恢复。

### 2.2 可恢复与当前可见分开

每个可见片段绑定 `entry_id + content_part + UTF-8 byte range + digest`。路径不是历史版本：旧文件按当时保留的源内容读取，当前文件另外通过原工具重新观察。历史回读不能刷新 `ObservedFiles` 的当前版本。

模型只允许引用当前请求或此前确实暴露过的来源范围。能证明“这个片段来自这里”，不能证明它支持模型的语义结论。没有意义的引用照样可能存在，必须由模型评测发现。

原始历史记录持续保留；只读检索默认当前 Session。结构化字段优先，词法搜索补充；缺少匹配词时可按 turn/step/path 查询相邻原文。FTS5 是可重建缓存，失败时仍可精确读原文。中英文分词、标识符拆分和路径归一化保留精确通道，不以 BM25 代替事实身份。

## 3. 方案一：State Workspace（状态工作集，首选）

### 3.1 核心机制

每次收到已确认结果，程序先更新执行事实。模型在下一次正常决策里修改有变化的工作状态，同时决定下一批任务动作、保留或释放哪些材料。没有变化的状态不重新生成。

一次正常响应的内部语义是：

```text
基于哪份请求/状态版本
+ 本次观察中哪些已处理
+ 工作判断的局部更新
+ 原文保留/释放意图
+ 下一步任务动作
```

这不是供应商已有的 `state_patch` 字段。正式接线必须选择实际受支持的 structured/tool 合同；原型的 `decide()` 只是验证后的内部入口。

用户约束和执行事实不放进允许 LLM 任意 `upsert/delete` 的字典。模型可删除的只是自己的判断项；项目要求是否失效必须有新的用户指令或可验证的任务作用域变化。

### 3.2 什么信息退役

已处理且未被当前状态/显式保留关系需要的过程材料可以离开 prompt；代码、diff、未理解的错误继续原样留在工作集。状态不存 `all_commands/all_errors` 这种无限追加数组。

文件更新只证明旧内容不是当前版本，**不证明旧内容已经没有比较价值**。新成功结果也不自动消除之前失败的原因。比较任务显式保留所需的多个版本；已排除假设保存紧凑理由与来源，而不是全部失败日志。

未处理观察和未闭合工具批次不得淘汰。状态补丁失败时，保留旧状态和未处理原文，不能为了腾空间把还没有承接的内容删掉。

### 3.3 模型与执行时序

```text
工具结果先落盘
→ host facts 更新（成功、失败、未知各自表达）
→ 组装请求，固定 source cut 和 state revision
→ 模型产生局部判断更新与下一动作
→ 校验引用、版本、预算和操作合法性
→ 提交状态变更
→ 下一动作经现有 ToolExecutor 执行
→ 实际结果确认后，更新执行事实
```

绝不在执行动作前把“准备修改/测试”写成“修改成功/测试通过”。需要纠正或重试的状态更新仍须计入模型调用成本。

### 3.4 预期收益与主要风险

重复调试同一问题时，当前状态主要被替换，不按尝试次数重放全部过程；跨文件任务可以保留多个活跃子问题而不保留全部日志。代价是模型要持续维护状态，漏写、误归纳或过早认为观察已处理会影响后续行动。

因此选择它不是因为结构化 JSON 天然可靠，而是它把大量反复推断的工作变成局部更新，并把精确事实从这种更新中隔离出来。

## 4. 方案二：Evidence Workspace（原文工作集）

### 4.1 核心机制

使用同一事实归约、来源系统和增量视图，但不要求模型维护“当前问题的语义摘要”。当前工作主要由以下材料承接：

```text
有效任务契约
+ 最新已确认执行事实
+ 当前涉及对象的原文槽位
+ 模型明确保留的原文
+ 短接续历史与未处理观察
```

对象槽位不是无限历史列表。例如 `(path, version, region)` 的当前材料、某一验证范围对应的最新结果；旧版本失去“当前”位置，但仍能作为比较材料被显式保留。工具 call/result 的关系属于精确结构，不能据时间相邻捏造“这个修改修好了那个错误”的语义因果边。

模型可以标注关注对象、保留/释放原文、发起新工作周期；它不必每步撰写另一份语义状态。必要的决定原话作为原始 assistant 片段保存，不改写为新的事实。

### 4.2 为什么它不是普通滑动窗口

材料保留依据是对象身份、依赖与当前用途，而不只是年龄。很早的 API 约束、正在比较的旧实现可以比刚出现的冗余日志存活更久。工作预算不允许无限保留所有对象；非活跃对象退到原始轨迹，留下有界入口，不把全索引装进 prompt。

### 4.3 预期收益与主要风险

需要精确代码和证据、模型不擅长持续维护状态时，减少语义改写有直接价值。缺点是模型每步需要从更多原文里重新理解工作，跨很多对象的开放式任务可能需要更大窗口或更多回读。

这不是主方案的低配版。它独立回答：**是否仅靠有身份、有生命周期的原文，就能获得足够好的长任务表现，而不承担持续语义状态的错误率。**

## 5. 两者共同的缓存和预算控制器

状态更新、材料退役、prompt 重建是不同操作。

一个短工作周期的请求由固定快照与按序追加的增量组成。增量包括新事实、状态 patch、仍需要处理的观察及必要动作接续。模型能立即看见更新，不必等下一次快照才获得新状态。

在自然工作边界、待淘汰材料积累、增量预算到达或实际容量不足时，代码从已提交记录重新物化快照；这不是再次调用模型写摘要。新快照须预留后续观察的空间，不能填到触发线附近导致每轮重建。

```text
触发预算（软） > 新快照目标
硬容量 = provider 实际窗口 - 输出预留 - 指令/工具/replay 占用
```

源码原型以字节为单位；正式实现必须按最终 adapter 输出的请求计量，并使用 provider usage 校准。给模型 128K 容量，不等于所有策略都应把工作集填到 120K。预算是独立参数，不能绑定最大窗口。

公共前缀相同只是缓存机会，不是实际缓存命中。缓存断点、cache-write 计费和 private continuation 必须按供应商能力处理；不能只删客户端消息，却让服务端 continuation 链重新带回完整历史。

立即重建可作同一控制器的消融，不增加新的 Session Strategy。若局部快照+增量经常被模型误解，直接快照版本可能胜出。

## 6. 增长与失真的粗评估

传统追加模式在两次压缩之间约为 `C[t+1] = C[t] + new_messages + new_results`。

新模式约为 `C[t] = contract + active_facts + active_state_or_evidence + pending + protocol`。旧材料退出量可抵消新材料进入量。规模应主要跟活跃问题的复杂度相关，而非已执行步骤数。

这不是对任意任务的 O(1) 无损承诺。新增大量有效约束确实需要更多表示空间。保护材料超容量时，应给出明确容量错误或有依据的重新分工，不得删约束伪造恒定内存。

| 维度 | 状态工作集 | 原文工作集 |
|---|---|---|
| 重复调试的冗余驻留 | 预期较低 | 可通过对象替换显著降低 |
| 精确证据 | 原文/来源保证，状态本身不保证 | 原文直接保留，更少改写 |
| 语义维护负担 | 较高，需要局部状态更新 | 较低，需要正确材料选择 |
| 多对象问题输入量 | 预期更紧凑 | 预期更大 |
| 错误主要形式 | 漏写/误改状态、过早消费观察 | 错误淘汰、原文整合失败、额外回读 |
| 缓存 | 共用增量控制器；patch 也占用输出/输入 | 通常较少 patch，但原文占用更多 |

未给成功率百分比和成本倍数：没有真实模型数据支撑这些数字。

本次 120 步确定性模拟中，两个策略请求字节均保持有界、旧原文仍可读、恢复视图一致。状态脚本的正确更新由 fixture 提供，不能用它证明模型会做到。具体数值和未测指标在 `mechanics-results.json`，解释见 EVALUATION.md。

## 7. 已淘汰的独立方案与原因

- “把摘要改成状态表，到原阈值才更新”：没有改变过程材料的驻留方式。
- “只维护笔记，然后 new_context”：适合跨窗接续，但单独使用不解决窗内快速增长；把其安全换窗思想并入共同控制器。
- “每一步只留状态＋最新观察”：开放开发经常需要代码比较和局部连续推理；保留为压力消融，不作为产品候选。
- “纯引用目录，无活跃状态或材料”：模型仍需要频繁重建工作，目录也会增长。
- “强制全 REPL/CodeAct”：可能减少输出入口体积，但同时改变动作空间；不是本次状态策略的必选条件。
- “仿造 GDN/Titans tensor state、维护语义图或向量库”：API Harness 无对应训练或 hidden-state 能力；没有必要为类比增加体系。

## 8. 研究如何被综合采用

这些资料是机制来源，不是两候选的性能担保。

1. SKILL.state v3：采用同次决策带局部状态更新；不接受固定 schema 总能覆盖开放开发、也不把字段校验当事实校验。其 chars/tokens 列存在不一致，本文不移植表格性能。
   https://arxiv.org/html/2608.26263v3
2. Scroll：采用原文外置、稳定地址、按需投影与程序过滤；不强制复制持久 Python 内核。论文跨系统记忆排名不是统一模型对照，其仓库说明部分评测复现资产当时仍私有。
   https://arxiv.org/html/2608.21690v1
   https://github.com/niceIrene/QwenPaw/tree/scroll-research
3. Codex `0df39752cbc4b88d0194ec62bdb0d56fbda4b014`：采用可独立于摘要的安全窗口生命周期、模型预算提示、可恢复外部状态。其 notes/history 使用专用后端，不作为 Singularity 可直接调用的公共能力。
   https://github.com/openai/codex/blob/0df39752cbc4b88d0194ec62bdb0d56fbda4b014/codex-rs/core/src/compact_token_budget.rs
   https://github.com/openai/codex/blob/0df39752cbc4b88d0194ec62bdb0d56fbda4b014/codex-rs/ext/history-notes/src/tools.rs
4. DSH `d347e703908d0406b7a7ef80e3a0e594d86b2215`：采用日志与模型视图分离、原文定位和来源关系；不复制通用 surface 插件系统。DSH 常规 compaction 仍是摘要。
   https://github.com/deepseek-ai/deepseek-harness/blob/d347e703908d0406b7a7ef80e3a0e594d86b2215/packages/core/session/src/surface.ts

   https://developers.openai.com/api/docs/guides/prompt-caching
