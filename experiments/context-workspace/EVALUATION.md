# 评估计划与本次确定性结果

## 1. 大致判断，不伪装成已测胜负

首选状态工作集：它能直接替代已经处理的过程材料，预期在反复调试和长时间多步骤任务中更紧凑。主要不确定性是模型的状态维护质量，而不是代码能否保存JSON。

原文工作集是重要备选：减少语义改写，但要重复读取和整合更多原文。若状态维护错误抵消节省，它可能是更可靠的选择。两者都应优于“给旧历史加一张状态表但不释放任何东西”这一结构上的冗余，实际任务优势仍待实测。

没有给出虚构成功率、节省比例和模型调用次数。代码生成的统计不等于模型测评。

## 2. 本次实际完成

命令：

```sh
python -m unittest discover -s experiments/context-workspace -p "test_*.py" -v
python experiments/context-workspace/benchmark.py --steps 120 --output experiments/context-workspace/mechanics-results.json
```

23 项机制测试通过。Python 3.13.5；标准库；没有模型请求、任务工具执行或API费用。测试包括策略不可变、闭合批次、引用UTF-8边界、范围暴露、原始材料隔离、状态预算原子性、用户约束保护、版本时效、召回去重、待处理观察保护、视图恢复与撕裂尾行。

模拟数值（**字节而非tokens**）：

| 120步场景 | 策略 | 平均请求UTF-8字节 | 最大请求字节 | 重建周期数 |
|---|---|---:|---:|---:|
| 重复操作1个对象 | 状态工作集 | 8,195.48 | 9,887 | 61 |
| 重复操作1个对象 | 原文工作集 | 9,314.52 | 12,433 | 41 |
| 轮流操作6个对象 | 状态工作集 | 9,282.62 | 11,027 | 61 |
| 轮流操作6个对象 | 原文工作集 | 12,115.28 | 15,288 | 41 |

每次运行均恢复了所探测的3条旧原文，重新打开后的已提交视图一致。状态脚本每次只根据当前观察更新对应对象的槽位，不预读未来，但正确更新由fixture直接给出；不是模型自己学会了更新。

这个实验只说明：控制器有能力停止无界历史重放；语义状态比原始块更紧凑、也消耗额外patch输入/输出；稳定前缀存在大小与重建频率的取舍。**不能据此说状态方案比Summary便宜多少、模型一定不丢约束，或者实际检索成功率是100%。**

原文组只保留预算允许的活跃对象子集，状态组保存脚本生成的较小槽位；两组的语义覆盖并不等价。这是待真实任务评估的取舍，不是公平任务排名。

模拟中的 `unbounded_replay_*` 是故意不裁切的体积参照，绝不是当前Summary。`mean_common_prefix_bytes_NOT_cached_tokens` 只是文本匹配上界，无法预测供应商实际缓存。整个baseline或任务费用一律不从这些字段推出。

## 3. 真实对照分组

主实验只比较当前Summary与两个新候选，不扩展成一长排论文克隆。

- S0：固定原始提交的Summary，用于回归。
- S1：共用原文存储/回读/计量基础设施的Summary，用于公平架构比较。
- W1：StateWorkspace。
- W2：EvidenceWorkspace。

补充两个必要控制：S1加简单旧tool-result遮蔽，检查复杂设计是否值得；W1禁用语义状态或立即重建，分别隔离状态收益和缓存调度。输出入场策略、history能力、工具封装改动必须各组一致，或单独做消融，不能只让新方案得到更好输入。

## 4. 任务与轨迹

至少覆盖以下任务族，并把专门测试失真的题目与普通开发任务分开报告：

| 任务族 | 关键错误模式 | 验收方法 |
|---|---|---|
| 同文件多次修改/编译/测试 | 日志累积、重复失败尝试、旧文件被当当前 | 最终代码测试+版本轨迹 |
| 多文件重构并禁止改公开API | 早期约束丢失、多对象工作集不足 | API快照/隐藏测试 |
| 排除方案后绕回同类错误 | 状态理由误写、已排除假设被遗忘 | 原因来源+实际行动 |
| 双版本实现比较 | 过早释放旧版本、按新旧序误判相关性 | 精确diff/输出 |
| 长日志中段关键错误 | 入场截断漏掉证据 | 精确错误恢复+修复成功 |
| 测试先通过后修改 | 旧验证被误当最新 | 校验验证发生的版本 |
| 任务转向再返回 | 状态作用域、恢复未完成事项 | 两子目标均验收 |
| 中文指令/路径符号线索 | 词法发现困难、只靠英文关键词 | 原文与结构查询 |
| 中断/恢复/未知工具结果 | 重复副作用、半提交状态 | 注入故障+副作用计数 |
| 合法JSON但语义错误 | 校验器把格式当正确性 | 对照实际证据与行为 |

固定轨迹用于测试投影和信息保存，未来提问在checkpoint之后揭示。闭环开发使用同一初始仓库和工具环境，但允许策略自然产生不同轨迹；不能把一组真实工具结果强塞给另一组不同状态的环境。

## 5. 指标

主指标：最终task success、最终版本的verification success、约束违反、重复副作用。模型自称完成不能判成功。

效率：每次请求真实input tokens、output/reasoning、cached input、cache writes、管理专用请求/修复请求、工具往返、端到端时间、总费用。记录provider未上报项为unknown，费用按实际价格合同算，不能用统一公式双计cache写入。

增长：输入随步骤变化曲线；按材料类别的新增/退役量；同一原文被重复携带的次数；rebase次数；protected/pending区大小；在相同token预算下能完成多少有效工作。

状态：不正确覆盖、无依据删除、当前/过时验证混淆、无法回读、知道要回读但没找到、找到后误用。后两项和存储可恢复率分开。

缓存：随机化运行顺序，分开cold/warm；固定模型/路由/工具顺序/断点布局；避免对照组互相预热。不能用最长公共文本前缀当cached_tokens。

## 6. 参数与判定

先做小规模校准确定任务时长、预算与方差，然后在留出任务上比较；参数不得针对隐藏题答案调优。建议扫描工作预算16K/32K/64K tokens（前提是模型可容纳），而不是原型中的字节数；扫描新快照占预算比例、短tail大小、最大语义状态量。所有状态、引用目录和工具schema都算输入。

每任务做配对重复，记录失败任务而非只报平均成功样本。用按任务重采样的置信区间和配对成功比较；不能用一次运行的1–2个成功差异宣布胜负。允许先预注册可接受的成功率差距及对应成本收益，不事后迁就候选。

决策顺序：真实性和协议/恢复合同先过关；其次最终任务成功与约束；再比较成本、延迟和工程复杂度。若W1不可靠、W2稳定则选W2；若共同基础设施+简单遮蔽的S1同样好，则保留Summary而不是为了“新机制”强上工作集。

本轮没有运行原用户机器上的 `Singularity-Evaluator`，也没有生产Rust测试结果。付费真实模型测试按仓库要求，在具体任务、模型和预算确定后再获得用户同意。
